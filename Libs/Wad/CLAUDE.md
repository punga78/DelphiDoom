# Libs\Wad — note per Claude

`Libs\Wad` (issue #46, primo passo) è la libreria a classi che sostituirà `Base\w_wad.pas` e le unit `w_*`; **il motore la usa per la directory dei lump**: `Base\w_wad.pas` crea un `IWadDirectory` (`wad_directory`), apre ogni file con `TWadFileSource`/`TSingleFileSource` sopra gli stream del motore (`Base\DelphiDoom.Wad.DStreamAdapter.pas`, `TDStream` visto come `TStream`) e rifà `lumpinfo[]` da lì con `W_SyncLumpInfo`; `lumpinfo[]` è una vista di sola lettura (nessuno la scrive), la ricerca per nome (`W_CheckNumForName*`) e i flag dei marcatori vengono dal `IWadFinder`; anche i byte dei lump passano dalla libreria (`W_ReadLump` chiama `ILumpReader.ReadLumpInto`, che legge dalla sorgente dritto nel buffer, senza copie; un file aggiunto con `~` è un `TReloadableWadSource` che non tiene il file aperto) mentre la cache resta lo zone memory del motore (`lumpcache[]`, `PU_*`; decisione: la cache è del motore). `lumpinfo[]` non è più visibile fuori da `w_wad.pas`: gli altri moduli usano `W_GetNameForNum`, `W_LumpLength`, `W_LumpFlags` e `W_LumpIsNamed`. `Base\w_wadreader.pas` (`TWadReader`) e `Base\w_wadwriter.pas` (`TWadWriter`) sono facciate con la vecchia API sopra `TWadFactory.OpenPath` e `IWadBuilder`: il WAD che scrive ha il layout della libreria (dati allineati a 4 byte, directory in fondo), non quello di prima (directory subito dopo l'intestazione, senza allineamento), quindi i file di cache `pk3sounds_<sha1>.wad`, `voxelsprite_<sha1>.wad`, `pk3tex_*`/`pk3flat_*` si rigenerano una volta; un nome di lump può avere qualsiasi byte tranne #0 (1–8 caratteri). Anche `Base\w_pak.pas` (il file system PAK: PAK Quake, PK3/PK4, WAD2/WAD3 e WAD con `PK3ENTRY`/`HI_START`/`TX_START`) legge le directory dei contenitori con la libreria (`TWadFactory.OpenPath`, `TWad2FileSource` per WAD2/WAD3) e apre ogni voce con `TPakEntryReader` (`Base\DelphiDoom.Pak.EntryReader.pas`: legge tutti i byte della voce e non va mai oltre la sua fine). Le regole del motore sui percorsi (issue #146) sono classi pure della libreria: `TPakIndex` (`DelphiDoom.Wad.Pak.Index`, `IPakIndex`: le voci con nome a 255 e nome corto a 64 caratteri come i vecchi `ShortString`, la tabella hash dei nomi corti a 8192 catene, l'ultima voce aggiunta vince, ricerca per percorso intero, nome corto, con cartella e con le cartelle preferite, anche la ricerca seriale, e l'hash globale sui byte dell'immagine della vecchia voce, `TPakEntryImage` di 588 byte, che finisce nei nomi dei file `pk3tex_*`/`pk3flat_*`), `TPakPathResolver` (`IPakPathResolver`: un file su disco vince, poi il modo, la cartella data a parte prima o dopo, e la seconda prova come percorso con cartelle) e `TPakNames` (hash dei nomi, con il `toupper` di `d_delphi` che guardava solo il byte basso, e le cartelle di `PAK_GetDirectoryListFromString`), create da `TWadFactory.CreatePakIndex`/`CreatePakResolver`. Il file system è `TPakFileSystem` (`Base\DelphiDoom.Pak.FileSystem.pas`, `IPakFileSystem` e `IPakContainers` di `DelphiDoom.Pak.Intf`): riceve `IEngineWadServices` (che ora crea anche indice e regole), legge i contenitori, tiene i file in attesa prima di `PAK_InitFileSystem` e apre i file con `TPakFileStream` (`DelphiDoom.Pak.Stream`); `ComposePak` lo crea e lo dà a `PAK_Configure`. `w_pak.pas` è ridotta alla vecchia API procedurale (`TPakStream` come sottoclasse di `TPakFileStream`, `pakmode_t`, `PAK_*`) per i moduli che la usano ancora; le classi del motore (`TEngineDynLightServices`, `TEngineVoxelFileSource`, `TEngineVoxelSpriteGenerator`, `TEngineAutoLoadSink`, `TEngineTextureFiles`) e `r_translations`, `r_pk3textures` e il FLATINFO di `r_data` ricevono il file system dal composition root. Verifica (issue #146): con il vecchio `TPakManager` copiato nello stesso eseguibile (harness temporaneo, poi tolto) e i due file system caricati con gli stessi file (PK3 con nomi lunghi, doppie barre, nomi non ASCII e WAD interni, PAK, WAD2, WAD con `PK3ENTRY`, `HI_START`/`TX_START` di ogni formato e lump corti, IWAD, una cartella, un file doppio, un PK3 rotto, un file sconosciuto e uno mancante) 5952 ricerche (63 nomi, anche file su disco, per 4 modi, 6 elenchi di cartelle preferite e 4 cartelle) danno le stesse risposte (esistenza, dimensione, byte letti, `Seek`/`Position`, voci con lo stesso nome corto, testi di `PAK_StringIterator`/`ReadFileAsString`/`ReadAllFilesAsString`, cartelle) con l'hash globale, i nomi e ogni voce aperta per numero: 35806 controlli, zero differenze. Difetto conservato: `PAK_AddFile` di una cartella diversa da quella corrente apre i file con il solo nome (`findfiles` dà nomi senza cartella), quindi li cerca nella cartella corrente. Lo ZIP lo legge `System.Zip` e `ZLIB\z_files.pas` non esiste più. **Composition root del motore**: `DelphiDoom.Engine.Composition` (`ComposeEngine`, chiamata come primo passo dal programma di ogni gioco, dopo `I_InstallCrashLogger`, e dal `begin` dei `ddc_*`) crea `TEngineWadServices` (`Base\DelphiDoom.Engine.Wad.Services.pas`, unico punto del motore che conosce `TWadFactory`, i sorgenti e gli adattatori) e lo dà, come `IEngineWadServices` (`DelphiDoom.Engine.Wad.Intf`), a `W_Configure`, `TWadReader.Configure`, `TWadWriter.Configure` e (tramite `TPakFileSystem`) a `PAK_Configure`; senza di essa quelle unit danno un `I_Error`. `w_wad`, `w_wadreader`, `w_wadwriter` e `w_pak` non usano più classi concrete della libreria. Le funzioni `W_*` restano l'API del motore (circa mille chiamanti): non si migrano una per una. Contratto in `DelphiDoom.Wad.Intf`: `IWadSource` (una sorgente di lump: `TWadFileSource` per IWAD/PWAD/DWAD, `TPakFileSource` per i PAK Quake, `TZipFileSource` per i PK3, `TFolderSource`, `TSingleFileSource`), `IWadDirectory` (le sorgenti una dopo l'altra, `Truncate` per il reload; vince l'ultimo lump con lo stesso nome), `IWadFinder` (`CheckNumForName` con i flag `TYPE_FLOOR/SPRITE/PATCH/VOXEL/HIRES` delle coppie `F_START`/`F_END`..., `CheckFirstNumForName`, ricerca in un intervallo), `ILumpReader`, `ILumpCache` (livelli `Static` e `Cache`, `Purge`), `IWadBuilder` (crea e modifica WAD; dati allineati a 4 byte, nomi maiuscoli di 1–8 caratteri). `TWadDirectory` implementa directory, finder e reader; `TWadFactory` è l'unico punto che conosce le classi concrete (`OpenPath` riconosce WAD, PAK, ZIP e cartelle dal contenuto). `DelphiDoom.Wad.Level.Types` ha i record dei lump di livello (THINGS, LINEDEFS, SIDEDEFS, VERTEXES, SEGS, SSECTORS, NODES, SECTORS, anche Hexen) packed e senza puntatori, con `SizeOf` coperto da test. Le interfacce di `DelphiDoom.Wad.Intf` usano tipi gestiti (`TBytes`, `string`); per la DLL ci sono interfacce a buffer e interi in `DelphiDoom.Wad.Dll.Intf` (`IWadDll`, `IWadDllSource`, `IWadDllDirectory`, `IWadDllBuilder`, `stdcall`, testi UTF-8 con buffer del chiamante e protocollo "nil per chiedere la lunghezza", codici `WADDLL_*`, nessuna eccezione oltre il confine). `DDWad.dll` (`Libs\Wad\DDWad.dpr`, `Tools\build.bat Libs\Wad\DDWad`, esporta `DDWadCreate`) è fatta da `TWadDllEngine` e dagli adattatori `Dll.SourceAdapter`/`DirectoryAdapter`/`BuilderAdapter`; `TWadDllClient` (`Dll.Client`, con `ClientSource`/`ClientDirectory`/`ClientBuilder`) la espone con le interfacce della libreria (`IWadSource`, `IWadDirectory`, `IWadFinder`, `ILumpReader`, `IWadBuilder`), `TWadDllLoader` la carica. Le sorgenti e le directory di un client lavorano insieme, non con quelle delle classi della libreria; ogni oggetto della DLL (e i temporanei, come finder e lettore ottenuti da una directory) va rilasciato prima di scaricarla. Il motore non usa la DLL (le sue sorgenti sono stream di `TDStream`, che non attraversano il confine): è per strumenti e per il server MCP (#47). `IWadDirectory.ReplaceSource` serve al reload (`~file`, `W_Reload`) e a `W_RuntimeLoad` quando lo stesso WAD viene caricato di nuovo. Test in `Tests\DelphiDoom.Tests.Wad` (156 prima della #48, che ne ha aggiunti 12; di cui 24 sulla DLL e 47 sulle regole del file system PAK, anche quella vera in `bin\Libs`); quelli sui WAD reali leggono `bin\<Gioco>` e si saltano se mancano.

**File system di id Tech 4 (issue #99, prima fetta)**: port di `framework\FileSystem.cpp` di Doom 3 (GPL v3 con termini aggiuntivi: intestazione "Based on the Doom 3 GPL Source Code" nelle unit `DelphiDoom.Wad.Fs.*`), nella stessa libreria ma separato dalla directory dei lump (`IWadDirectory` cerca per nome di lump, questo per percorso relativo). Unit: `Fs.Types` (`TGameFsSettings` = i cvar, `TGameSearchFlags` = `FSFLAG_*`, `TGameSearchPath`, `EGameFsException`), `Fs.Intf` (`IGameDisk`, `IGamePack`, `IGamePackLoader`, `IGameFile`, `IGameFileSystem`), `Fs.Paths` (`TGameFsPaths`: `HashFileName` a 1024 secchi, `FilenameCompare` con `\` e `:` come `/`, `BuildOSPath`, controlli di `OpenFileReadFlags`, ordine dei percorsi con `TIdStrings.IcmpPath` di IdLib), `Fs.Disk` (`TGameDisk`), `Fs.Pack` (`TGamePack`), `Fs.PackLoader` (`TZipPackLoader`), `Fs.GameFile` (`TGameFile`), `Fs.FileSystem` (`TGameFileSystem`), `Fs.Factory` (`TGameFileSystemFactory`, unico punto che conosce le classi concrete). `Zip.Intf` (`IZipArchive`) e' implementata da `TZipFileSource`, che ora ha anche un costruttore da stream (posseduto o no): niente secondo lettore ZIP. Dipende da `Libs\IdLib` (`TIdMd4.BlockChecksum` per `pack_t.checksum`, `TIdStrings.IcmpPath`); il progetto di test elenca le unit di IdLib nel `.dpr`. **Regole dell'originale conservate**: la lista si cerca dall'ultimo elemento aggiunto; i pak di una cartella stanno subito dopo la cartella, dall'ultimo in ordine che ignora le maiuscole (`idStrList::Sort` usa `Icmp`); il nome di una voce e' in minuscolo con `/`, la ricerca passa dalla tabella hash (due nomi uguali per `FilenameCompare` ma con `:` al posto di `/` cadono in secchi diversi e non si trovano: difetto dell'originale, coperto da test); con una voce doppia nello stesso pak vince l'ultima; il filtro `gamedir` vale solo per le cartelle, non per i pak (in ricerca e negli elenchi); gli elenchi di un pak dipendono dalle voci di cartella dello ZIP (`sound/sub/`) per mostrare le sottocartelle; nomi elencati dai pak in minuscolo; `ListFiles` unisce senza duplicati (`Icmp`) nell'ordine della lista di ricerca. **Differenze**: i nomi sono `string` Unicode (maiuscole solo A-Z); `ReadFile` non aggiunge lo `0` finale; `ListFiles` con percorso vuoto non legge fuori dalla stringa come l'originale (`name[pathLength - 1]` con `pathLength` 0 e' un accesso prima dell'inizio del buffer di `idStr`); i pak si leggono dallo stream aperto dal disco iniettato (non thread safe); `IGameDisk.ListFiles` non restituisce `.` e `..` (il file system li toglie). **Non portato**: scrittura (`OpenFileWrite`, `WriteFile`, `fs_copyfiles`), server pure, `addon.conf` (solo il riconoscimento), `binary.conf`, `ListMods`, journal, chiavi, `FindDLL`, download, `fs_caseSensitiveOS`, `idFile` a pezzi (`Seek`/`Read`). **Parita'**: `Tests\Source\DelphiDoom.Tests.Wad.GameFileSystem.pas` (68 test; 259 nel progetto, a 32 e a 64 bit) con valori prodotti da `Tests\Data\Wad\GameFs\fsparity.cpp`, il C++ di Doom 3 (`HashFileName`, `FilenameCompare`, il ciclo di `GetFileList` sui pak e `GetFileListTree`) compilato con `bcc32c` di Embarcadero (nessun file di Doom 3 nel repository); copertura delle unit nuove tra 94% e 100% (`TZipFileSource` 90%). Non collegato al motore.
